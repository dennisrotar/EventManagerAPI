# Event Manager Microservices

Система управления мероприятиями, построенная на микросервисной архитектуре с событийно-ориентированным взаимодействием через Apache Kafka.

## Архитектура

Решение разделено на 3 независимых микросервиса (каждый со своей базой данных PostgreSQL) и 1 разделяемый проект с контрактами:

1. **Users Service** (порт 5001) — регистрация, вход, генерация JWT-токена. БД: `users_db`.
2. **Events Service** (порт 5002) — управление событиями (CRUD) и учёт доступных мест. БД: `events_db`.
3. **Bookings Service** (порт 5003) — создание и отмена броней. БД: `bookings_db`.
4. **EventManager.Shared** — библиотека классов с общим контрактом события `BookingConfirmedEvent` и именами топиков Kafka.

## Взаимодействие (Eventual Consistency)

Сервисы не вызывают друг друга по HTTP напрямую. Обмен происходит через Apache Kafka:

- При подтверждении брони (в фоне) сервис **Bookings** сохраняет статус `Confirmed` в свою БД и публикует событие `BookingConfirmed` в топик Kafka. Ключом сообщения выступает `EventId` для гарантии порядка обработки.
- Сервис **Events** подписан на этот топик. При получении сообщения он:
    1. Проверяет идемпотентность (через таблицу `ProcessedMessages` в БД Events), чтобы не списать места дважды при повторной доставке.
    2. Уменьшает количество доступных мест у соответствующего события.
    3. Сохраняет ID сообщения и изменения в одной транзакции.

## Аутентификация

- Токен выдаёт только сервис **Users**.
- Сервисы **Events** и **Bookings** проверяют токен с помощью общих секрета, издателя и аудитории.
- Управление событиями (POST/PUT/DELETE) доступно только роли `Admin`. Эндпоинты броней требуют обычной аутентификации.

## Наблюдаемость (Observability)

В проект интегрирован стек мониторинга и трейсинга:

|Инструмент|Назначение|Порт|URL|
|---|---|---|---|
|Prometheus|Сбор и хранение метрик|9090|[http://localhost:9090](http://localhost:9090/)|
|Jaeger|Сбор и просмотр распределённых трейсов|16686|[http://localhost:16686](http://localhost:16686/)|
|Grafana|Визуализация метрик на дашбордах|3000|[http://localhost:3000](http://localhost:3000/)|

### Что настроено

- **OpenTelemetry SDK** подключён во всех трёх сервисах.
- **Трейсы:** автоматическая инструментация HTTP и EF Core. Экспорт в Jaeger через OTLP.
- **Метрики:** инструментация ASP.NET Core и .NET Runtime. Доступны по `/metrics`.
- **Логи:** Serilog с `CompactJsonFormatter` (вывод в консоль в JSON).
- **Дашборд Grafana:** настроен через provisioning. Содержит панели Latency, Throughput, Error Rate, а также метрики рантайма (.NET GC Heap, Thread Pool).

## Запуск

> [!important]
> **Важно!** Команду `docker compose up` необходимо выполнять из папки `EventManager.Microservices`.

Для запуска всей системы необходим Docker.

```bash
cd EventManager.Microservicesdocker compose up --build
```

- Users API: [http://localhost:5001/swagger](http://localhost:5001/swagger)

## Стратегия кеширования

В сервисе Events реализован паттерн **Cache-Aside** с использованием Redis.

### Что кешируется:

1. **Получение события по ID** (`GET /events/{id}`)
    
    - Ключ: `event:{id}`
    - Стратегия: Инвалидация при записи (Cache Invalidation).
    - При обновлении (`PUT`) или удалении (`DELETE`) события данные сначала сохраняются в БД, а затем соответствующий ключ удаляется из Redis.
    - Также при обработке Kafka-сообщения (подтверждение брони), которое уменьшает количество свободных мест, кеш этого события инвалидируется. Следующий запрос прочитает актуальные данные из БД и прогреет кеш.
2. **Топ-10 самых популярных событий** (`GET /events/top`)
    
    - Ключ: `events:top10`
    - Стратегия: Гибридная (TTL + Инвалидация при структурных изменениях).
    - Обновление по TTL: При высокочастотных операциях бронирования (через Kafka) кеш топа не инвалидируется, чтобы не создавать избыточную нагрузку на Redis. Список обновляется автоматически по истечении TTL (5 минут) — небольшое устаревание рейтинга некритично.
    - Инвалидация: Кеш топа принудительно удаляется только при структурных изменениях события (создание нового, обновление лимита мест, удаление), чтобы исключить выдачу неактуальных записей.

### Значения TTL:

Вынесены в конфигурацию `appsettings.json` -> `CacheSettings`.

- `EventByIdTtl`: 10 минут.
- `TopEventsTtl`: 5 минут.

### Отказоустойчивость (Graceful Degradation):

Сервис корректно стартует и работает даже если Redis недоступен при запуске. Подключение `ConnectionMultiplexer` настроено с флагом `AbortOnConnectFail = false`. При недоступности Redis ошибки логируются, но не пробрасываются клиенту — запросы прозрачно деградируют до прямого обращения к базе данных PostgreSQL.
